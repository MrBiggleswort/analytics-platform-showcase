# Аналитическая платформа - публичная витрина

## О репозитории

Это публичная витрина текущей версии коммерческой аналитической платформы, которая
разрабатывается как замена предыдущей системы с ELT внутри PostgreSQL.

В новой версии основная оркестрация и обработка данных перенесены в Python.
PostgreSQL остается DWH и транзакционным контуром состояния, Airflow управляет
параллельной обработкой клиентов, а Superset работает поверх опубликованного
семантического слоя.

Репозиторий не является копией рабочего проекта. Реальные клиенты,
рабочая конфигурация, инфраструктура, секреты, точные бизнес-правила и
часть SQL удалены. Код адаптирован так, чтобы показать архитектуру и характер
решаемых задач без публикации коммерческого продукта.

Репозиторий намеренно не является готовым к установке релизом.

## Чем эта версия отличается от предыдущей

В предыдущей версии загрузка, преобразования, бизнес-модели и витрины в основном
выполнялись PL/pgSQL процедурами внутри центральной PostgreSQL базы.

В новой версии обязанности разделены:

- Airflow управляет пакетными запусками и параллельной оркестрацией тенантов;
- Python отвечает за источники, нормализацию, загрузку, DQ и пересчеты;
- PostgreSQL хранит слои `raw`, `stage`, `mart`, `control` и `published`;
- у каждой сущности есть независимая отметка прогресса;
- внешние ключи источников отделены от внутренних числовых ID;
- ошибки одного тенанта не должны блокировать остальных;
- первичная историческая загрузка отделена от ежедневного инкрементального режима;
- семантическая публикация происходит через проверенный снимок;
- восстановление, сверка и очистка по сроку хранения вынесены в отдельные процессы;
- миграции версионируются и проверяются по контрольной сумме;
- один рабочий контур используется для облачной и локальной поставки.

Подробное сравнение находится в
[docs/legacy-modernization.md](docs/legacy-modernization.md).

## Загрузка из нескольких источников

Источники подключаются через единый интерфейс. Конкретный тенант может читать
данные из CSV, Firebird, REST API или PostgreSQL-интеграции.

Адаптер не решает, как устроен DWH. Он возвращает записи сущности в
каноническом формате, а общий процесс добавляет контекст тенанта, сохраняет данные в `raw`
и продолжает нормализацию.

## Рабочая конфигурация клиента

Один клиент представлен одной конфигурацией `ClientConfig`. В ней задаются
идентификатор тенанта, список `clinics[]`, тип источника и режим получения данных.

Тенант и клиника не смешиваются в один идентификатор: один тенант может
содержать несколько клиник, а физическая площадка МИС и внешний ID клиники
остаются отдельными сущностями.

Получение данных поддерживает два режима: управляемый (`managed`) и внешний (`external`). Для CSV один тенант
может иметь несколько выгрузок, но каждая выгрузка должна относиться к клинике из
`ClientConfig.clinics[]`. Конфигурация проверяется до запуска обработки.

Переходная копия клиентской конфигурации из прежней системы после проверки
функционального паритета удалена. `ClientConfig` остается единственным актуальным
источником рабочей конфигурации.

Подробнее:
[docs/client-runtime-contract.md](docs/client-runtime-contract.md).

## Барьер получения данных

Каждый пакетный запуск начинает получение данных от всех активных тенантов одновременно.

Барьер ждет конечный ответ от каждого тенанта, а не успешные данные от всех.

В публичной версии используются состояния:

- `success`;
- `failed`;
- `no_fresh_data`;
- `timeout`.

У всей волны один предельный срок. В рабочей системе он равен 120 минутам от начала
получения данных. Отдельный клиент не может продлить этот срок.

Явная ошибка доступа или источника фиксируется сразу.

Подробнее:
[docs/acquisition-barrier.md](docs/acquisition-barrier.md).

## Слои raw, stage и mart

### Слой raw

Слой `raw` хранит исходную запись вместе с техническим контекстом:

- `tenant_id`;
- `source_system`;
- `entity_name`;
- `payload`;
- `record_key`;
- `source_updated_at`;
- `load_run_id`;
- `extracted_at`.

Слой `raw` используется как хранилище исходных данных, источник повторной обработки и база для диагностики.

### Слой stage

Слой `stage` содержит нормализованные сущности.

Ключевой принцип:

- внешний идентификатор хранится без изменения смысла в `source_key`;
- внутренний PK/FK является положительным `bigint`;
- внутренние соединения не зависят от формата ID источника;
- одинаковые `source_key` разных тенантов не конфликтуют.

### Слой mart

Слой `mart` строится поверх `stage` и содержит аналитические модели. В публичной версии
оставлены упрощенные примеры выполнения назначений и выручки. Полная коммерческая
матрица правил не публикуется.

## Состояние инкрементальной загрузки

Одна глобальная отметка прогресса слишком груба для разнотипных сущностей.

Поэтому `visits`, `sales`, `sale_services` и другие сущности имеют отдельные
курсоры.

Отметки прогресса продвигаются транзакционно вместе с успешной публикацией. Если
последующая обработка не завершилась, курсор не должен выдавать незавершенную загрузку
за успешную.

## Идентификация сущностей источника

Внешний идентификатор может быть числом, GUID, составной строкой или другим
непрозрачным ключом.

Он нормализуется до стабильного текстового представления и регистрируется в
`control.source_key_registry`.

Реестр возвращает внутренний положительный bigint ID.

Такой подход позволяет подключать разные МИС и не использовать текстовые или UUID-ключи в
часто выполняемых внутренних соединениях.

Подробнее:
[docs/source-identity.md](docs/source-identity.md).

## Пересчеты по влиянию изменений

Дата изменения записи в источнике и бизнес-дата события не обязаны совпадать.

Если старый факт исправлен сегодня, процесс добавляет затронутое окно в
`control.recalculation_queue` и пересчитывает нужный период, а не всю историю.

## Качество и свежесть данных

Проверки качества данных разделены на уровни:

- проверка контракта источника;
- проверки до загрузки в `stage`;
- согласованность данных в `stage`;
- инварианты витрин `mart`;
- SLA по свежести данных;
- проверка перед публикацией.

Свежесть отдельно учитывает факт успешной связи с источником и отметку прогресса бизнес-события.

## Публикация семантического слоя

Superset не должен видеть полусобранный набор данных.

Семантический слой проходит последовательные состояния:

```text
building
validated
published
retired
```

Новый снимок сначала полностью строится и проверяется. После этого текущий
снимок тенанта переключается на новую версию одной транзакцией.

## Изоляция тенантов

`tenant_id` проходит через слои `raw`, `stage`, `mart`, `control` и `published`.

Изоляция не оставлена только на уровне фильтра BI. Она встроена в хранение,
состояние обработки, идентификацию источников, DQ, пересчеты и публикацию семантического слоя.

## Миграции

Механизм миграций:

- сортирует версии;
- считает SHA-256;
- берет служебную блокировку PostgreSQL;
- сверяет контрольную сумму уже примененных версий;
- фиксирует каждую миграцию отдельно;
- корректно обрабатывает ошибки SQL;
- поддерживает проверочный запуск без изменений.

## Оркестрация Airflow

Кроме ежедневного ELT в рабочей версии есть отдельные DAG для сверки,
восстановления свежести, очистки старых семантических снимков и DWH.

В публичной версии основной DAG сокращен до архитектурно значимых частей.

## Развертывание

Рабочий контур включает PostgreSQL, Redis, Airflow и Superset.

Облачная и локальная поставка используют одинаковые образы приложения. В закрытом
контуре образы могут поставляться автономно.

`deploy/compose-topology.yml` показывает только топологию. Реальные имена образов,
тома, порты, проверки состояния и секреты не публикуются.

## Тестирование

В рабочем проекте есть модульные и интеграционные тесты для барьера получения данных,
готовности CSV, адаптеров источников, идентификации сущностей, миграций, изоляции
тенантов, преобразований `raw -> stage` и `stage -> mart`, публикации семантического слоя и защиты
рабочего контура.

Публичная версия содержит несколько контрактных тестов, чтобы было видно, какие свойства
архитектуры считаются обязательными.

## Что намеренно не опубликовано

В репозитории отсутствуют:

- рабочая конфигурация клиентов;
- реальные ID тенантов;
- названия клиентов;
- IP, адреса сервисов и учетные данные;
- полный набор сопоставлений источников;
- точная логика выполнения назначений;
- точные правила отнесения выручки;
- исходные дашборды Superset;
- рабочий манифест релиза;
- полный список миграций;
- секреты развертывания;
- пути к резервным копиям;
- SQL, специфичный для конкретных источников;
- полная реализация функционального паритета с предыдущей системой.
