# Архитектура новой платформы

## Общая модель

Новая версия строится как многоклиентская платформа данных с разделением
получения данных, хранения состояния, преобразований, публикации и BI.

Рабочий контур состоит из пяти логических зон:

1. Адаптеры источников.
2. Оркестрация получения данных.
3. Обработка в DWH.
4. Публикация семантического слоя.
5. Доступ BI.

## Адаптеры источников

Источники имеют разные свойства:

- файл появляется целиком;
- API отдает данные страницами;
- Firebird читается через SQL;
- PostgreSQL-источник может читаться через отдельное подключение;
- источник может поддерживать `updated_at`, а может не поддерживать его.

Основной процесс не должен знать детали транспорта. Поэтому он работает с
интерфейсом `SourceClient`.

Адаптер возвращает последовательность записей одной сущности. Далее общий
процесс добавляет контекст тенанта, вычисляет ключ записи, сохраняет данные в `raw`,
фиксирует статистику и продолжает нормализацию.

## Рабочая конфигурация клиента

Один клиент представлен одной конфигурацией `ClientConfig`.

`ClientConfig` содержит `clinics[]`, тип источника и настройки получения данных.
`tenant_id`, внешний ID клиники и физическая площадка источника считаются
разными сущностями. Один тенант может включать несколько клиник без создания
дополнительных аналитических тенантов.

Конфигурация проверяется до обращения к источнику. После завершения перехода
прежняя копия клиентской конфигурации больше не используется в рабочем контуре.

## Получение данных как отдельная фаза

В рабочем DAG получение данных отделено от преобразования.

Источник одного тенанта может готовить выгрузку несколько десятков минут, а
другой вернуть данные сразу. Если соединить ожидание и обработку в одну
последовательную задачу, медленный источник будет задерживать всю платформу.

Общая волна позволяет всем тенантам начать проверку готовности одновременно.

## Слои хранения

### Слой raw

Слой `raw` хранит исходную запись максимально близко к формату источника.

Он нужен для повторной обработки, аудита, контроля прогресса источника,
диагностики и определения затронутых данных.

### Слой stage

Слой `stage` хранит нормализованные предметные сущности.

Каждая строка включает `tenant_id`. Внутренние связи используют числовые
суррогатные ID, внешние ключи сохраняются отдельно.

### Слой mart

Слой `mart` содержит аналитические модели и агрегаты. Сюда не должны попадать частично
преобразованные записи источников.

### Семантический и опубликованный слои

Семантический слой дает стабильный контракт для BI.

Слой `published` хранит версионированные снимки опубликованных наборов данных.

## Служебный контур control

`control` является отдельным слоем состояния обработки.

В нем находятся:

- запуски загрузки;
- пакетные запуски;
- прогресс по отдельным сущностям;
- контрольные точки порций данных;
- волны получения данных;
- реестр внешних ключей;
- результаты DQ;
- результаты проверки свежести;
- очередь пересчетов;
- состояния семантических снимков;
- журнал миграций.

Так служебное состояние не размазывается по бизнес-таблицам.

## Транзакционные границы

Отметка прогресса продвигается только вместе с успешной публикацией.

Это защищает от ситуации, когда курсор источника ушел вперед, а последующий слой `mart`
не был построен.

## Изоляция тенантов

Область тенанта применяется на каждом уровне:

```text
конфигурация источника
raw
stage
mart
control
семантический слой
published
доступ BI
```

Тенант является единицей блокировки, восстановления, исторической дозагрузки,
DQ, очистки по срокам хранения, публикации и прав доступа.

## Служебные DAG

Ежедневная загрузка не перегружается всеми видами обслуживания.

Отдельные процессы выполняют сверку, восстановление устаревших данных, очистку
старых снимков и очистку данных по срокам хранения.
