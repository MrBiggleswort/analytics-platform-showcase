# Рабочая конфигурация клиента

## Одна конфигурация ClientConfig на тенант

Во время работы платформа не собирает настройки клиента из нескольких независимых
таблиц и переходных слоев совместимости.

Один клиент представлен одной конфигурацией `ClientConfig`.

В ней задаются:

- идентификатор тенанта;
- список `clinics[]`;
- тип основного источника;
- режим получения данных;
- параметры, специфичные для выбранного транспорта.

Публичная версия не содержит рабочих значений конфигурации и реальных записей
клиентов.

## Тенант и область клиник

Тенант и клиника не являются одним и тем же объектом.

Один тенант может включать несколько клиник. При этом внешний ID клиники,
физическая площадка МИС и внутренний `tenant_id` не обязаны совпадать.

Принадлежность клиник хранится плоским списком `clinics[]`. Это позволяет
обрабатывать один тенант целиком без создания отдельного аналитического тенанта
для каждой физической площадки.

## Тип источника

`source_type` определяет способ чтения основного источника:

```text
csv
firebird
rest_api
onec_api
```

Код, специфичный для конкретного транспорта, остается внутри адаптера источника.
Основной процесс получает единый контракт `SourceClient` и не зависит от того,
откуда физически пришла запись.

## Режимы получения данных

Получение данных поддерживает два режима.

Управляемый режим (`managed`) означает, что платформа сама инициирует получение данных или напрямую
читает источник.

Внешний режим (`external`) означает, что выгрузка готовится внешним процессом, а платформа
проверяет только ее готовность и свежесть.

Для CSV один тенант может иметь несколько выгрузок. Каждая выгрузка должна
относиться к клинике, уже указанной в `ClientConfig.clinics[]`.

## Проверка конфигурации до запуска

Конфигурация валидируется до запуска обработки.

Примеры обязательных инвариантов:

- `tenant_id` положительный;
- `clinics[]` не пуст;
- ID клиник внутри одного тенанта не дублируются;
- CSV-выгрузка не может ссылаться на клинику вне области тенанта;
- CSV в режиме `managed` требует настройки запуска выгрузки;
- CSV в режиме `external` не должен содержать такую настройку;
- источники, отличные от CSV, работают в режиме `managed`.

В рабочем проекте этот контракт реализован через Pydantic и проверяется на этапе
предварительной проверки, а также отдельными архитектурными тестами.

## Почему переходная конфигурация удалена

На переходном этапе часть метаданных клиента могла одновременно существовать в
новой конфигурации и в хранилище предыдущей системы.

После проверки функционального паритета `ClientConfig` стал единственным
актуальным источником рабочей конфигурации. Переходная копия была удалена
миграцией, а новая установка сразу создает схему без нее.

В публичной версии конкретное имя прежней таблицы и служебные данные рабочей
миграции намеренно не публикуются.
