# Барьер получения данных

## Задача

Все активные тенанты начинают проверку источника одновременно в начале общего
пакетного запуска.

Барьер ждет конечный ответ от каждого тенанта. Успешные данные от всех клиентов
для прохождения барьера не требуются.

## Конечные состояния

В публичной версии используются четыре состояния:

```text
success
failed
no_fresh_data
timeout
```

`success` означает, что данные готовы к дальнейшей обработке.

`failed` используется для явной ошибки источника или доступа.

`no_fresh_data` означает, что до общего предельного срока не появился новый
полный набор данных.

`timeout` означает, что операция не успела завершиться в пределах общего срока.

## Общий предельный срок

Предельный срок принадлежит всей волне получения данных, а не отдельному
тенанту.

В рабочей системе общий срок составляет 120 минут от начала волны.

Клиент, который начал повторную попытку незадолго до конца срока, не получает
новый двухчасовой интервал.

## Явные ошибки

Такие ошибки завершают получение данных для тенанта сразу:

- ошибка аутентификации;
- HTTP 401;
- HTTP 403;
- отказ в соединении;
- отсутствующий обязательный источник;
- ошибка протокола источника.

## Готовность CSV

Для файлового источника одного `mtime` недостаточно.

Рабочий подход:

1. Проверяется наличие полного набора обязательных файлов.
2. Набор должен оставаться стабильным заданный период.
3. Для каждого файла рассчитывается описание текущего состояния.
4. Новый набор сравнивается с предыдущей успешной загрузкой.
5. Свежим считается только весь обязательный комплект целиком.

## Барьер получения данных в Airflow

Названия задач ниже оставлены как реальные технические идентификаторы:

```text
start_acquisition_wave
        |
        + тенант A: получение данных
        + тенант B: получение данных
        + тенант C: получение данных
        |
wait_for_terminal_states
        |
acquisition_barrier
        |
        + тенант A: обработка, если `success`
        + тенант B: пропуск, если `failed`
        + тенант C: пропуск, если `no_fresh_data`
```

Сенсор Airflow отвечает за ожидание, а актуальное состояние хранится в
PostgreSQL в слое `control`.
